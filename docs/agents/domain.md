# Domain docs

## Read before exploring

Read the root `GLOSSARY.md` and relevant decisions under `docs/adr/` when present. If either is absent, proceed silently. Create domain documentation as terms or decisions are resolved through the domain-modeling workflow.

## Layout

Use a single context: one `GLOSSARY.md` at the repository root, with architecture decision records in `docs/adr/`.

## Vocabulary

Use the glossary's terms when naming domain concepts in issues, code, hypotheses, and tests. When a needed term is missing, check whether an existing term fits; record genuine gaps for domain modeling.

## Decision conflicts

Explicitly identify any existing ADR contradicted by a proposed change, and explain why the decision should be reconsidered.
